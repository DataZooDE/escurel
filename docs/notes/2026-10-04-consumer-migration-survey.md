## 0. How to read this

- **own pages** = markdown pages with `type: skill|instance` frontmatter that live in the repo itself (what `migrate-kind-files --apply` rewrites).
- **vendored** = nested git repositories/submodules (`vendor/escurel`, `vendor/agent-template`, `.claude/worktrees/*`): the tool never enters them (they belong to another history); they are updated by bumping the pin, not by editing in place.
- **writers** = code, prompts, templates and test fixtures that WRITE or TEACH `type: skill|instance` (not pages). After the cut the engine refuses those writes with `frontmatter_type_removed`. These need a human edit (a text replace in format strings is enough, but a data field named `kind` must be renamed FIRST, see 1.1).

4. **Vendored consumers are internally consistent until they bump the pin.** Their tests build the PINNED escurel (`vendor/escurel/crates/escurel-test-support`), so nothing breaks the day the engine is released. The cut bites a consumer when it (a) bumps its pin, or (b) talks to a DEPLOYED new engine. 5. **Deploy-time lock-step (the unavoidable part).** A new-engine tenant refuses `type:` writes; an old engine refuses `kind:` pages. A consumer that writes pages at runtime (herkules agent, carl memory, heron, evolve, reef, agent-template products) therefore has to ship its `kind:` change in the SAME maintenance window as the engine (stop-first: stop consumer + engine, back up the data dir, start the new engine: the tenant boots quarantined, run `migrate-kind`, start the new consumers). If that window is too tight, the owner can choose to cut a TRANSITIONAL engine release first (the parser from commits `be9aeee`..`ce6ea9e` reads both keys and writes `kind:`) and the hard cut one release later; that contradicts the recorded decision "no escape hatch", so it is NOT assumed here.

6. **Pinned-by-rev git dependency:** `anofox-evolve` pins `escurel-*` by git rev `ca6ab07` (escurel main before the cut): it keeps compiling until the rev is bumped, and then needs the `page_type`/`resume_cursor` changes below.

7. **String-form `actions:`** (removed in 0.7.0): the dry run found 0 skill pages with string actions in any consumer repo (the tool checks every parsed skill page). 19 files in 5 repos mention `actions:` (herkules 3, heron 1, anofox-evolve 4, datazoo-ai-engineering 10, hetzner-agent-substrate 1); none is a skill page with string ids, but their Rust/Dart fixtures should be eyeballed for string-form `actions:` inside embedded page text (the tool parses files, not string literals).

## 4. Suggested rollout order

**Principle:** consumers are lock-stepped to the engine only at DEPLOY time (finding 1.4/1.5). Prepare every consumer on a branch first (no engine change needed to prepare), then flip engine + consumers in one stop-first window per environment.

**Phase A: prepare (any time before the window, no risk to production)**
1. Rename the data fields named `kind` (collisions): `datazoo-loops` skill `system` (`kind` -> `system_kind`, 2 instances + the skill's `fields:`), herkules + substrate seeds `tabelle_skill` / `foliensatz_skill` (`kind: code` -> e.g. `skill_kind: code`, and the Rust code that reads it). Re-run the dry run: `conflicts` must be 0.
2. In each repo with own pages run `escurel admin migrate-kind-files --path .` (dry run), read the diff, then `--apply` on a clean tree and commit as one reviewable commit. Order by blast radius, smallest first: `anofox-evolve` (10), `datazoo-ai-engineering` (23), `hetzner-agent-substrate` (55; the herkules seeds come from herkules: do them together), `herkules` (30 seeds), `carl` (158), `datazoo-loops` (166).
3. Edit the WRITERS (table in section 2): replace the `type: skill|instance` format strings in src/scripts/prompts first, then the test fixtures, with `kind:`; `page_type` -> `page_kind` (carl `src/memory.rs`, heron `cloud/crates/heron-escurel/src/lib.rs:579`, evolve `crates/evolve-escurel/src/lib.rs`, herkules docs); `resume_cursor` -> `next_cursor` (anofox-evolve `crates/evolve-agent/src/serve.rs`). The new code must NOT be deployed against an old engine (it writes `kind:`).
4. Bump pins on branches, in dependency order: `datazoo-agent-template` (vendor/escurel) -> `heron` (vendor/agent-template) and the `-p4`/`-p5`/`agt-wt-tenant` clones; `herkules` and `carl` (vendor/escurel); `anofox-evolve` (git rev `ca6ab07`); path-dependency repos (`peacock`, `datazoo-ai-engineering`) follow whatever checkout is next to them. Run each repo's own real-stack test suite against the new pin.

**Phase B: the window (per environment, stop-first; see `docs/deploy/consumer-rollout.md`)**
1. Stop the consumers (herkules, carl, heron, evolve, reef, agent-template products), then the engine. Back up each tenant data dir (tar with the server stopped: the real restore point).
2. Start the NEW engine image: each un-migrated tenant boots QUARANTINED (`/readyz` 200 with `x-escurel-quarantined: 1`, MCP answers `tenant_quarantined`).
3. Run `escurel admin migrate-kind --tenant <t>` (dry run: pages, drafts, snapshots; conflicts must be empty), then `--apply`. Signed pack `base/` pages are skipped: re-export and re-sign the pack before the window.
4. Start the new consumer versions; smoke one write and one read per consumer.
5. Rollback: stop everything, restore the tar, start the OLD engine image + OLD consumers.

**Phase C: after**: delete the old branches; keep the dry-run command as a CI guard in repos that hold page files (a clean dry run means no legacy page re-entered).

## 5. Top risks

1. **Runtime writers not updated in the window** (herkules `src/knowledge.rs`/`src/tool.rs`, carl `src/memory.rs`, heron, evolve, reef): their writes fail with `frontmatter_type_removed` the moment the new engine is live; the symptom is an agent that "works" but cannot save. Mitigation: grep gate `git grep -E "type:[[:space:]]*(skill|instance)"` must be empty in src before the window.
2. **Data fields named `kind`** (herkules code skills, loops `system`): a blind `s/type:/kind:/` would create duplicate keys; the tool refuses them, but a human doing it by hand will not.
3. **Prompts that teach agents the old key** (templates, scaffolds, skill docs: carl `skills/README.md`, `seed/ki-gipfel-2026/README.md`; peacock `crates/peacock-core/src/author.rs` scaffold and `saved.rs`; evolve patches): agents will keep writing `type:` until the text changes; they need updating even though they are not "code".
4. **Vendored submodule pins move in lock-step** (agent-template -> heron chain): bumping one without the other builds a product on a template that vendors a different escurel.
5. **Deployed tenants with open drafts / CRDT history** (herkules `.local` tenant, any substrate tenant): covered by `migrate-kind` (drafts rewritten with a new hash + audit event), but it refuses while a CRDT session is live: schedule the window when no editor session is open.
6. **Signed packs**: a tenant subscribed to a pack with legacy `base/` pages stays quarantined until the publisher re-exports and re-signs.
7. **Concurrent edits in the consumer repos**: `anofox-evolve` (and `datazoo-loops`, `peacock`, `herkules` with uncommitted work) are being edited right now; run `--apply` only on a clean tree (the tool refuses otherwise).
